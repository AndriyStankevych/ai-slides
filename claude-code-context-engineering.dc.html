01 · How the model readsMECHANICS · 02

One Pass, No Memory

The model is stateless. Every turn, the client re-sends the entire conversation and the model reads it from scratch, start to finish, once.

TURN 1
prompt + tools sent, answer returned, nothing retained
TURN 2
turn 1 re-sent in full, plus everything the tools printed
TURN 20
nineteen turns of history compete with your actual question
01 · How the model readsMECHANICS · 03

Everything Is One Flat List

system prompt
CLAUDE.md
tool definitions
file contents
tool output
your question

There is no hierarchy in the window. A rule you wrote in CLAUDE.md and a stack trace a test printed carry the same weight when the model reads them.

Attention is the only ranking, and it is driven by position and repetition, not by your intent.

01 · How the model readsMECHANICS · 04

Lost in the Middle

high
startmiddleend
recall of a single fact by its position in the window

The beginning and the end of the window are read reliably. The middle is where a requirement quietly stops being applied.

Put standing rules in a file that loads at the top. Put the current task in your last message. Distrust the middle.

Quality vs. Fill

UNDER 40%
Sharp
follows rules, asks when unsure, edits narrowly
40 – 70%
Drifting
forgets a convention, re-reads files it already read
OVER 70%
Sloppy
contradicts earlier decisions, invents paths, loops

The failure is gradual and quiet. By the time the session hits its limit, the answers have been getting worse for a while.

02 · The context windowMECHANICS · 07

/clear and /compact

/clear
Window back to zero. New topic, no residue.
keeps: files on disk, CLAUDE.md, your plan file loses: every decision that lived only in chat
/compact
The session replaced by a summary of itself.
keeps: the thread of what you were doing loses: detail, silently and unpredictably

/context shows the meter before you have to choose.

03 · The leversMECHANICS · 12

Nested CLAUDE.md in a Monorepo

monorepo/
├── CLAUDE.md — at start
└── packages/
    ├── api/
    │   ├── CLAUDE.md
    │   └── orders.ts
    └── web/
        ├── CLAUDE.md
        └── cart.tsx

Only the root file is loaded up front. A package file joins the window the first time the agent opens a file under it.

The practical effect: context grows in proportion to what the task actually touches, instead of to the size of the repository.

03 · The leversMECHANICS · 14

Skills: Progressive Disclosure

Level 1
ALWAYS LOADED
Name and one-line description of every installed skill. Tens of tokens each.
Level 2
ON TRIGGER
The body of SKILL.md enters the window when the description matches what you asked for.
Level 3
IF THE SKILL ASKS
Reference files, templates and scripts the skill links to, read only when it needs them.

Twenty skills can be installed and cost almost nothing until one of them is the right skill.

Anatomy of a Skill

name: release

  Use when asked to ship or
  publish a version.
---
## Steps
1. Read CHANGELOG.md …
Write the description as a trigger
It is the only part the model always sees. "Use when…" beats a noun phrase every time.
One procedure per skill
A skill that does four unrelated things triggers on all four and helps with none.
Push detail down a level
Long checklists and templates go in linked files, not in the body.

Slash Commands

A markdown file in .claude/commands/ becomes a slash command. Its text is your prompt, with arguments substituted in.

You choose when it runs. That is the whole difference from a skill.

/review
the review checklist you keep pasting
/fix-ci
read the failing job, propose the smallest patch
/spec <ticket>
arguments make one command serve many tickets

When a Sub-agent Pays Off

03 · The leversPRACTICE · 20

The Plan on Disk

Write the plan as a task list in the repo. The agent re-reads it at the top of each session and marks progress in it.

You get a reviewable artifact, and the window gets a checkpoint it can reload instead of remember.

tasks/checkout-refactor.md
[x] extract price rules from cart.tsx
[x] unit tests for the rules module
[ ] swap cart.tsx to the new module
[ ] delete the old branch in checkout.ts
03 · The leversMECHANICS · 21

Hooks

Shell commands fired on lifecycle events. They run whether or not the model felt like it.

SessionStart
inject the branch, the ticket, today's state
PreToolUse
inspect, and refuse, before the tool runs
PostToolUse
format and lint every file the agent writes
Stop
run the tests before the turn is called done
A rule in a file is a request. A hook is a guarantee, and it costs no context.
03 · The leversMECHANICS · 22

Permissions and Deny

allow
the tools and commands that never need a prompt
ask
the default: you approve each time
deny
blocked at the tool layer, not negotiable in prose

Secrets, production credentials, migrations against a live database, force-pushes: these are deny entries, not paragraphs in CLAUDE.md.

Every rule you move from prose to configuration is a rule that cannot be forgotten in the middle of a long window.
03 · The leversMECHANICS · 23

MCP Servers

A standard protocol for handing the agent tools it did not ship with. The repo gets a .mcp.json; the agent gets new verbs.

issue tracker
read the ticket instead of you pasting it
database
inspect a real schema, not a guess
browser
drive the app it just changed
internal service
your own API, exposed once for everyone

The value is removing the human copy-paste step between a system of record and the agent.

What MCP Costs You

WINDOW AT SESSION START

6 servers
12 servers

Each server publishes every tool it has, with schemas and descriptions. All of it loads up front, on every request, used or not.

Connect servers per project rather than globally, and disconnect the ones this repo never calls. A tool you might need someday is charged today.
