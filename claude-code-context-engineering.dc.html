LLM (Large Language Model)

Two Kinds of Knowledge: the model brings what it was trained on. Everything about your codebase has to be sent to it as text.

TRAINED IN · FROZEN
the weights
language semantics, algorithms, idioms library and framework APIs as of the training cutoff patterns from public code, in general, not in particular
Does not change while you work. The model learns nothing from your session.
SENT AT RUN TIME · PER REQUEST
the context
your instructions and your question the files, diffs and tool output the CLI collected your conventions, your architecture, your names
This is the only part you control, and the whole subject of this talk.
01 · How the model readsMECHANICS · 03

One Pass, One Token at a Time

At run time the model does one thing: read the context so far, predict the token most likely to come next, append it, and repeat. It keeps nothing between turns — the client re-sends the entire conversation and the model reads it from scratch, once.

01 · How the model readsMECHANICS · 04

Everything Is One Flat List

system prompt
CLAUDE.md
MEMORY.md
tool and MCP server definitions
skill names and descriptions
sub-agent descriptions
file contents
tool output
your question

There is no hierarchy in the window. A rule you wrote in CLAUDE.md and a stack trace a test printed carry the same weight when the model reads them.

Skill — a folder with a SKILL.md of instructions for one procedure. Only the name and description sit in the window; the body loads when it is used.
MCP server — a connected source of extra tools. Its tool definitions sit in the window from the first token, whether or not you call them.
Memory — notes Claude writes for itself across sessions. The MEMORY.md index loads every session; its topic files are read on demand.
Sub-agent — a specialist with its own context window, system prompt and tool access. Its description sits in your window; its work does not, only the summary it returns.
01 · How the model readsMECHANICS · 05

Lost in the Middle

high
startmiddleend
recall of a single fact by its position in the window

The beginning and the end of the window are read reliably. The middle is where a requirement quietly stops being applied.

TOP  standing rules, in a file that loads with the session BOTTOM  the task you want done, in your last message MIDDLE  everything you are hoping it still remembers
LENGTH WIDENS IT
the middle of a long session is a far bigger target than the middle of a short one
RESTATE, DO NOT REFER
say the constraint again in the current message rather than pointing back at where you said it
NOT A CLAUDE QUIRK
measured across models: recall by position, not by how much you meant it
02 · The context windowMECHANICS · 06

Quality vs. Fill

UNDER 40%
Sharp
follows rules, asks when unsure, edits narrowly
40 – 70%
Drifting
forgets a convention, re-reads files it already read
OVER 70%
Sloppy
contradicts earlier decisions, invents paths, loops

The failure is gradual and quiet. By the time the session hits its limit, the answers have been getting worse for a while.

03 · The leversPRACTICE · 07

Leave vs. Extract

The file is loaded in full at the start of every session, so every line is a recurring cost. Keep the facts that always apply; move the conditional ones somewhere that loads on demand.

LEAVE · EVERY SESSION
role and boundaries: what this repo is, what not to touch the four commands: build, test, lint, run naming and conventions the team actually enforces where the truth lives: spec.md, adr/, docs/
EXTRACT · LOADED ON DEMAND
skills/ — multi-step procedures, pulled in when needed .claude/rules/ — rules for one part of the repo hooks — anything that must happen every time, enforced permissions.deny — hard blocks, not polite requests
WRITE IT THE SECOND TIME
the same mistake twice, the same correction retyped, or something a new teammate would need
CONCRETE ENOUGH TO CHECK
"use 2-space indentation", not "format code properly"; two rules that contradict get picked between arbitrarily
UNDER 200 LINES
longer files cost more and are followed less; /init starts one, /doctor proposes trims
03 · The leversMECHANICS · 08

Nested CLAUDE.md in a Monorepo

monorepo/
├── CLAUDE.md — at start
└── packages/
    ├── api/
    │   ├── CLAUDE.md
    │   └── orders.ts
    └── web/
        ├── CLAUDE.md
        └── cart.tsx

Only the root file is loaded up front. A package file joins the window the first time the agent opens a file under it.

The practical effect: context grows in proportion to what the task actually touches, instead of to the size of the repository.
UPWARD AT LAUNCH
every directory above your working directory is loaded and concatenated; the closest file is read last
DOWNWARD ON DEMAND
nested rules and skills follow the same rule: they arrive when Claude touches the directory
SKIP THE NEIGHBOURS
claudeMdExcludes drops other teams’ files by glob; keep it in settings.local.json

Sub-agents

YOUR WINDOW
the returned summary
SUB-AGENT WINDOW · DISCARDED
30 files, 4 searches, 2 failed test runs

It starts fresh: its own system prompt, the delegation message Claude writes, and your CLAUDE.md files. Not your conversation history, not the files already read, not the main conversation's auto memory.

THREE COME BUILT IN
Explore read-only search, Plan research in plan mode, general-purpose for multi-step work
ITS OWN EVERYTHING
own model, own tool list, own permissions — a reviewer can be denied Write and Edit outright
RUNS BESIDE YOU
it works in the background while you keep going, and its result arrives as a message when it finishes
03 · The leversPRACTICE · 11

Defining One Is a Markdown File

--- name: code-reviewer description: Reviews code for quality and best practices. Use after edits. tools: Read, Glob, Grep model: sonnet --- You are a code reviewer. Analyze the code and give specific, actionable feedback.
Frontmatter configures it, the body is its system prompt. Only name and description are required.
WHERE IT LIVES
.claude/agents/ — this project, checked into version control for the team ~/.claude/agents/ — you, in every project on your machine
THE FIELDS WORTH KNOWING
tools allowlist, disallowedTools denylist — drop Write and Edit to keep it read-only model — haiku, sonnet, opus or inherit; route cheap work to a cheap model skills preloads content, memory gives it a directory that survives sessions
The description is the routing mechanism and it sits in your window all session. Write it as the condition for delegating, and keep it short.
03 · The leversPRACTICE · 12

When a Sub-agent Pays Off

Delegate when the work is self-contained and the output is verbose. Keep it in the main conversation when the context is already there.

WORTH IT
wide search where the answer is short: "which module owns this table?" output you will never reference again — a test run reported as failures only a survey of an unfamiliar area before you commit to a plan independent investigations you can run in parallel, one agent each work you want fenced: a read-only agent that cannot Write or Edit
NOT WORTH IT
work that depends on decisions you made in this conversation anything you will have to re-explain in full to delegate tasks needing back-and-forth: it cannot ask you a question mid-run a quick, targeted change — a fresh agent has to gather context first edits where you want to watch each diff as it lands
SUMMARY, NOT TRANSCRIPT
ask for the shape of the answer you want back; the rest stays in its window
RESULTS STILL COST
many agents each returning a detailed report will fill your window anyway
FORK WHEN CONTEXT MATTERS
/subtask inherits the conversation, so you skip the re-explaining

Auto Memory Takes Its Own Notes

Claude accumulates knowledge across sessions without you writing anything. It saves four kinds of note for itself, and skips anything it can derive from the codebase.

useryour role, expertise and working preferences
feedbackcorrections you give Claude, approaches you confirm
projectongoing work, deadlines and decisions not in the code
referencewhere to find information outside the project
WHERE IT LIVES
~/.claude/projects/<project>/memory/
├── MEMORY.md
├── user_role.md
└── feedback_testing.md
The path is derived from the git repository, so every worktree of the same repo shares one directory. MEMORY.md is the index: the first 200 lines or 25KB load at the start of every conversation. Topic files are read on demand.
ON BY DEFAULT
toggle it in /memory, or set autoMemoryEnabled: false for one project
MACHINE-LOCAL
not shared across machines or cloud environments, and kept out of the transcript sweep
YOURS TO EDIT
plain markdown; open the folder from /memory to read, change or delete any of it
03 · The leversPRACTICE · 14

Sub-agents Can Keep Their Own

A sub-agent starts fresh every time and never sees the main conversation's auto memory. One frontmatter field gives it a directory that survives across conversations.

--- name: code-reviewer description: Reviews code for quality memory: project ---
user~/.claude/agent-memory/<agent>/ — learnings that apply across all projects
project.claude/agent-memory/<agent>/ — project knowledge, shared through version control
local.claude/agent-memory-local/<agent>/ — project knowledge kept out of the repo
PROJECT BY DEFAULT
the recommended scope: the sub-agent's knowledge is shareable with the team
PART OF AUTO MEMORY
turn auto memory off and the field has no effect; on, it brings Read, Write and Edit with it
ASK IT TO CURATE
tell it to consult memory before the work and save what it learned after
03 · The leversMECHANICS · 15

MCP Servers

A standard protocol for handing the agent tools it did not ship with. The repo gets a .mcp.json; the agent gets new verbs.

issue tracker
read the ticket instead of you pasting it
database
inspect a real schema, not a guess
browser
drive the app it just changed
internal service
your own API, exposed once for everyone

The value is removing the human copy-paste step between a system of record and the agent.

LOCAL · THE DEFAULT
private to you, in this project only — where an experiment belongs
PROJECT · COMMITTED
.mcp.json at the repo root gives the team the same servers; Claude asks before running one
USER · EVERYWHERE
available in all your projects; stdio, SSE or HTTP, OAuth through /mcp

Slash Commands

A markdown file in .claude/commands/ becomes a slash command. Its text is your prompt, with arguments substituted in.

You choose when it runs. That is the whole difference from a skill.

Diff: !`git diff main...HEAD` Standards: @docs/review.md Review $ARGUMENTS against them.
/review
the review checklist you keep pasting
/fix-ci
read the failing job, propose the smallest patch
/spec <ticket>
arguments make one command serve many tickets
IT CAN GATHER FIRST
a ! line runs bash and drops the output into the prompt; @path pulls a file in
YOURS OR THE REPO'S
.claude/commands/ ships with the project, ~/.claude/commands/ follows you everywhere
DISCOVERABLE BY DESIGN
frontmatter sets the description in the menu, so the team finds what exists instead of asking
03 · The leversMECHANICS · 18

Hooks

Shell commands fired on lifecycle events. They run whether or not the model felt like it.

SessionStart
inject the branch, the ticket, today's state
PreToolUse
inspect, and refuse, before the tool runs
PostToolUse
format and lint every file the agent writes
Stop
run the tests before the turn is called done
A rule in a file is a request. A hook is a guarantee, and it costs no context.
MATCHED TO A TOOL
configured in settings.json against a matcher, so a formatter fires on Edit and Write only
EXIT 2 BLOCKS
JSON on stdin, exit code back: 0 passes, 2 blocks and feeds stderr to Claude to correct
YOUR CREDENTIALS
hooks run as you, 60-second default timeout — review what you add; /hooks lists them

Anatomy of a Skill

---
name: release
description: cut a release —
  version bump, changelog, tag.
  Use when asked to ship or
  publish a version.
---
## Steps
1. Read CHANGELOG.md …
Write the description as a trigger
It is the only part the model always sees. "Use when…" beats a noun phrase every time.
One procedure per skill
A skill that does four unrelated things triggers on all four and helps with none.
Push detail down a level
Long checklists and templates go in linked files, not in the body.
THIRD PERSON, CONCRETE
name the terms someone would actually use; that wording is what the match runs against
BUDGETS ARE REAL
name and description under 1024 characters together; keep the body under roughly 500 lines
PERSONAL WINS
~/.claude/skills shadows .claude/skills on a name clash — the opposite of sub-agents
03 · The leversMECHANICS · 20

Skills: Progressive Disclosure

Level 1
ALWAYS LOADED
Name and one-line description of every installed skill. Tens of tokens each, present all session.
Level 2
ON TRIGGER
The body of SKILL.md enters the window when the description matches what you asked for.
Level 3
IF THE SKILL ASKS
Reference files and templates the skill links to, read only when it needs them. A script it runs costs nothing but its output.

Twenty skills can be installed and cost almost nothing until one of them is the right skill. Keep the index resident, keep the detail retrievable.

Session memory has none. A sub-agent does: .claude/agent-memory/<agent>/, committed and shared; agent-memory-local/ to keep it out.
No clash to resolve. One directory per repository for the session, one per agent name for sub-agents.

Managed → --agents → project → yours → plugin. Nested: closest to the working directory wins.

.claude/skills/<name>/SKILL.md
The other way round: enterprise over personal, personal over project. A personal skill shadows the repo one.
